# AIOps Intelligence Pipeline: Anomaly Detection, Log Mining, Incident NLP and Model Operations

Hands-on lab from the AIOps Additional Assessment Labs at Al Nafi.

## Scenario
An SRE team runs a checkout platform that produces three data streams: metrics (CPU, memory, latency, error rate, request rate), application logs, and incident tickets. The goal was to detect anomalies, mine logs, route tickets to the right team, and run it all as a containerised service with experiment tracking and drift monitoring. All data is synthetic and was generated by the lab.

## What I did
1. **Feature engineering:** built time-series features (trailing statistics with no look-ahead, z-scores, cyclical hour encoding) and shared one module between training and serving to avoid training/serving skew.
2. **Isolation Forest:** trained an unsupervised detector and chose the operating threshold from an alert budget on training data, not from test labels.
3. **Autoencoder (PyTorch):** trained a dense autoencoder on 10-minute windows and attributed detections to individual signals.
4. **Log mining:** used Drain3 to turn about 40,800 log lines into 8 templates, flagged rare templates, and fused log and metric alerts with OR and AND strategies.
5. **Ticket classification:** built a TF-IDF and logistic regression pipeline with cross-validated hyperparameter search and checked the learned top terms.
6. **MLflow:** tracked a parameter sweep, registered model versions, promoted the best with a `champion` alias, and queried everything through the REST API.
7. **Containerised API:** served the models with FastAPI in Docker, with input validation and a non-root user.
8. **Drift and retraining:** measured drift with PSI and KS, showed its impact on the live model, retrained, registered the new version, and redeployed.

## Results

### Metric anomaly detection (test set, 3 of 3 incidents detected by both)
| Model | Precision | Recall | F1 |
|-------|-----------|--------|----|
| Isolation Forest (3% alert budget) | 0.674 | 0.775 | 0.721 |
| Autoencoder (97th percentile threshold) | 0.681 | 0.800 | 0.736 |

The two detectors performed almost the same, so this lab doesn't show that one is better. Isolation Forest is cheaper and simpler to explain, while the autoencoder learns temporal shape.

### Log mining and signal fusion
About 40,800 log lines collapsed into 8 templates, of which 4 were rare. Combining the log signal with the metric detector changes the precision and recall balance:

| Strategy | Precision | Recall | F1 |
|----------|-----------|--------|----|
| Metrics only | 0.674 | 0.775 | 0.721 |
| Logs only (rare templates) | 0.690 | 0.750 | 0.719 |
| Fusion OR | 0.571 | 0.950 | 0.714 |
| Fusion AND | 1.000 | 0.575 | 0.730 |

OR catches almost everything (recall 0.95) but raises more false alarms, which suits paging. AND produced no false alarms (precision 1.0) but misses 42% of incident minutes, which suits automatic remediation where a wrong trigger is costly. Choosing between them is a policy decision, not a modelling one.

### Incident ticket classifier
Best settings were C = 1.0 with word unigrams and bigrams. Cross-validated macro-F1 was 0.956, and the held-out test set gave 0.96 accuracy and 0.96 macro-F1. About 4% of the labels are wrong on purpose, which caps the achievable score.

### Drift and retraining
| Feature | PSI | Status |
|---------|-----|--------|
| latency_ms | 6.70 | Significant |
| req_rate | 2.00 | Significant |
| cpu | 1.14 | Significant |
| error_rate | 0.008 | Stable |
| mem | 0.003 | Stable |

On the second day of the new week, the old model alerted on 13.8% of minutes (precision 0.276, with 144 false alarms). After retraining, the alert rate dropped to 4.7% and 118 false alarms were removed, with precision rising to 0.50. The trade-off is that recall fell from 1.00 to 0.62, so the new model misses more incident minutes. Both models still detected both incidents. Retraining on a single day is an emergency fix, because that day contained an incident and only one daily cycle, so a production policy would retrain on a rolling window and gate promotion on evaluation.

### Validation
The lab's validation script passed all 16 checks across the eight tasks.

## Debugging a container networking fault
The API container showed as healthy, but requests from the host returned "connection reset by peer". The cause was that Uvicorn was bound to `127.0.0.1` inside the container, so traffic arriving through Docker's published port never reached it. The health check passed only because it ran inside the container. I fixed it by binding to `0.0.0.0`, then rebuilt and redeployed. The key lesson is that a green health check doesn't prove a service is reachable from outside.

## What I learned
- Choosing a threshold from training data and an alert budget keeps evaluation honest.
- Point metrics and event recall answer different questions: how good the alerts are, and whether incidents were caught at all.
- PSI gives a size of drift that can be acted on, while KS p-values become tiny on large samples even for trivial shifts.
- Model operations need a registry with aliases, a rollback path (the old image stayed available), and a drift trigger.
